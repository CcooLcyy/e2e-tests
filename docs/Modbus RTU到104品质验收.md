# Modbus RTU 到 104 品质验收

用例归入 **Modbus RTU** 分组。通过 DSP 上位机打开预配置的 RTU 运行点表，通过独立 Msk104Master 会话观察协议结果。

## 运行前准备

准备已包含 RTU 品质上送实现的下位机、测试账号及支持独立测试会话的 Msk104Master。专用 RTU 连接、点表、采集任务、DataCenter 路由和 IEC104 从站均需提前配置并运行。专用 CA 的自发上送及总召数据使用短浮点遥测（类型 13 或 36）。目标点映射为带 CP56Time2a 时标的短浮点遥测（类型 36），目标的 IOA 不启用固定上送或模拟覆盖。设置正死区并将正常工程量和 104 报文数值都配置为 100。另准备同一 CA 下可正常总召的参照遥测。

目标点初始没有 DataCenter 样本。外部预置的 RTU 应答源应依次提供初始无响应、正常值 100、无响应、合法异常响应、恢复值 100，并为每个阶段留出观测时间。首次有效响应应晚于本例的总召终止及初始观察。请使用专用测试线路并预留窗口，避免主站保留的 500 条报文在取证前滚动覆盖。现有 slaveSim 的静态配置不足以自行编排这一时序，需要运行前安排具有该能力的独立应答源。

启用测试环境中的 104 主站并配置匹配的驱动，在 `local/modbus-rtu-104-quality.json` 写入专用观察配置。用例启动独立上位机副本，在界面填入 `manager_address` 连接专用下位机，再打开预置且正在轮询的 RTU 连接。旧配置缺少该字段时按示例补齐。下位机 RTU 模块的全局 MQTT 配置须已初始化。每次独立重跑前都须在测试外确认参照点有效、目标尚无 DataCenter 样本，并将应答源恢复到静默阶段。关掉上次的主站会话或只暂停 RTU 应答均不足以证明目标首值已清除。

```json
{
  "manager_address": "192.0.2.10:50051",
  "rtu_connection": "e2e-rtu-quality",
  "rtu_tag": "power",
  "master_host": "192.0.2.10",
  "master_port": 2404,
  "common_address": 1,
  "target_ioa": 100,
  "reference_ioa": 101,
  "phase_timeout_seconds": 20
}
```

在 `local/login-account.json` 配置专用平台账号。任务超时应覆盖会话初始化、四个阶段的等待及报文取证。

## 通过条件

1. 从 DSP 上位机的协议页面打开运行前准备好的专用连接，确认运行点表显示目标 tag。104 主站收到肯定的总召确认和终止，期间至少有一条同 CA 的正常参照遥测（COT=20）。总召响应和初始阶段的自发上送均不包含目标 IOA。
2. 总召后同 CA/IOA 的自发短浮点遥测（COT=3）按顺序上送 100，品质变化为 `0x00 → 0x40 → 0xC0 → 0x00`。两个故障阶段沿用相同的旧样本协议时标，恢复后的样本时标更新。保持同品质的重复采样可以存在。正常阶段的死区内采样可能比首条正常报文更新，因此旧样本时标以第一条 NT 报文为基准。
3. 证据保留主站可见的收发报文、解析结果、阶段预期和实际观察。前置缺失、断言失败和取证缺失各自保留实际原因。

用例中的总召用于读取协议快照。故障和恢复由预置应答源独立产生。某阶段等不到新的目标遥测时，用例保留最后主站行、上位机目标行及原始报文。主站未收到该阶段的品质不足以判断是外部工况尚未到达，还是已到达但上送异常，需结合本次应答源记录区分。
